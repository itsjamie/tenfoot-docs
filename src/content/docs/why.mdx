title: Why a renderer
description: The oldest TV sets the rules. What that means, and what Tenfoot's work costs on a speed test and on a full home screen.
---

Every TV app has to run on the oldest TV its company still supports. For LG and Samsung, that is a 2017 TV. Its browser is Chromium 38 (LG) or Chromium 47 (Samsung). It has no `fetch`, no WebAssembly, and no WebGL 2. Its chip is ten to fifteen times slower than a laptop. And its GPU does math with 16-bit numbers, even when it says it can do better.

Tenfoot treats that 2017 TV as the main target, not a special case. It uses newer features like WebGL 2 only when a newer TV has them.

| Device | Browser | WebGL 1 | WebGL 2 | Notes |
| --- | --- | --- | --- | --- |
| LG webOS 3.x (2016–17) | Chromium 38 | yes | no | the oldest: no fetch, no wasm, only part of ES6 |
| Samsung Tizen 3.0 (2017) | Chromium 47 | yes | no | GPU math is really 16-bit |
| Samsung Tizen 4.0 (2018) | Chromium 56 | yes | yes | first Samsung with WebGL 2 |
| LG webOS 5.x (2020) | Chromium 68 | yes | yes | first LG with WebGL 2 |
| Samsung / LG 2025 | Chromium 120 | yes | yes | WebGPU is possible, but not a target |

## How fast is it?

The Lightning team publishes an open speed test for TV renderers, [lightning-js/benchmark](https://github.com/lightning-js/benchmark). It makes, changes, and removes thousands of items with the CPU slowed down six times. These are Tenfoot's core on that test, run on September 17, 2026. Times are in milliseconds. Lower is better. The ± number shows how much the result moved between runs.

| Test | Tenfoot |
| --- | ---: |
| create 1,000 items | 3.94 ±2.4 |
| update 1,000 items | 4.52 ±2.4 |
| update every 10th | 2.84 ±0.8 |
| select one | 4.76 ±3.9 |
| swap two rows | 3.08 ±1.1 |
| remove one | 2.40 ±2.0 |
| create 10,000 items | 21.44 ±10.0 |
| add 10,000 items | 19.82 ±6.7 |
| clear | 2.96 ±3.7 |
| 20,000 items, memory | 3.17 MB · 28.5 ms |
| test page's JavaScript | 50.03 KB |

## How to read the table

**The clock stops when the renderer says "I'm done."** Tenfoot says it right after the frame it drew, so every time here includes drawing that frame.

**The big rows are the ones to watch.** Making 10,000 items, adding 10,000 more, and holding 20,000 in memory are where the real work is. On the small rows, the work is a few milliseconds and the ± is as large as the number.

**The page size is the published package.** It is all of the test page's JavaScript for `tenfoot` 0.1.0, built and minified the way the test builds it. About 43 KB of it is Tenfoot: the parts of the core the test uses, and the canvas text. The rest is the test's own code. The whole core, everything `tenfoot/core` exports, is 47 KB minified and 17 KB gzipped.

**These are desktop numbers.** The computer is a desktop with the CPU slowed down. It is not a TV. Numbers from real TVs are on the [roadmap](../roadmap/).

## A full home screen

Thousands of items on a test page are not an app. So we also measured a whole screen: nine rows of twenty movie posters, a hero picture that changes when you land on a tile, and a full-screen backdrop that fades from one picture to the next. A script presses Down eight times and Up eight times, twice, half a second apart. It runs in headless Chromium on the GPU, with the CPU slowed 1×, 6×, and 20×. These are from September 17, 2026.

| Metric | 1× | 6× | 20× |
| --- | ---: | ---: | ---: |
| frames a second, animating | 60.1 | 60.2 | 60.6 |
| worst frame, ms | 16.9 | 20.3 | 24.5 |
| CPU per frame, mean ms | 0.064 | 0.123 | 0.434 |
| CPU per frame, peak ms | 1.7 | 6.7 | 21.9 |
| key press, mean / max ms | 0.11 / 0.6 | 0.45 / 2.8 | 1.52 / 8.7 |
| draw calls | 11 | 11 | 11 |
| first picture, ms | 33 | 113 | 406 |

**It holds 60 frames a second at every speed.** The whole screen is 11 draw calls. The CPU number is the time spent inside paint. Text is drawn with the browser's canvas. At 20×, 19 frames out of 20 finish under 20 ms, and the worst takes 24 ms, so a frame is dropped now and then.

## What comes with it

A TV app needs more than drawing. Tenfoot also comes with:

- **Captions** that read the time straight from the video, so they stay in step through a skip or a pause. They follow the caption settings the viewer chose on the TV.
- **Compressed pictures** (ETC1 and DXT5, from KTX and PKM files) that live under a memory limit. When the limit is reached, the pictures used least recently make room.
- **Focus that feels right on a remote.** It remembers where you were in each row, keeps focus inside a menu or dialog while it is open, and puts it back where it was when it closes. It scrolls to keep the focused item in view, even in a list too long to build all at once. Every rule it follows is written down and tested.
- **Deep links** that open the right screen with Home beneath it, so Back leaves the app the way LG and Samsung require.
- **The store rules**: the exit dialog Samsung asks for and LG does not, keeping the screensaver away during video, working offline, and coming back cleanly when the TV relaunches the app.
- **Widgets**: cards, rows, grids, buttons, and menus, taken from [ARENA+](../reference-app/), the eleven-screen sample app they were built for and tested in.

## What it does not do

There is no template language and no data binding. A node is an object with a `paint` method. That simple design is where the speed comes from. If you want templates, Blits or SolidTV is a better fit. If you want to know what every frame costs, this is for you.
